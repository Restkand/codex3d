## Gambaran besar

<Aside type="note" title={"Model mental: Studio foto yang memotret 60 kali per detik"}>
Bayangkan sebuah studio. [Scene](/kamus/dasar/scene/) adalah panggungnya, berisi properti dan lampu. [Camera](/kamus/dasar/camera/) menentukan dari mana panggung itu difoto. [Renderer](/kamus/dasar/renderer/) adalah fotografer yang menekan tombol rana dan mencetak hasilnya ke `<canvas>`. Animasi muncul karena fotografer memotret **berulang kali**, dan sebelum setiap jepretan properti di panggung digeser sedikit.
</Aside>

Seluruh aplikasi Three.js, sesederhana atau serumit apa pun, mengikuti pola yang sama: **siapkan sekali**, lalu **ulangi terus**. Jika pola ini sudah dipahami, kode 3D mana pun akan lebih mudah dibaca, karena kamu tahu harus mencari bagian "persiapan" dan bagian "loop".

## Siapa mengerjakan apa: CPU dan GPU

Komputer punya dua prosesor yang bekerja sama ([CPU vs GPU](/kamus/dasar/gpu-cpu/)). Kode JavaScript-mu berjalan di **CPU**. CPU sebenarnya tidak menggambar piksel. Tugasnya menyiapkan data dan mengirim perintah ke GPU seperti "gambar mesh ini dengan material ini". Setiap perintah itu disebut [draw call](/kamus/performa/draw-call/).

**GPU** menerima perintah itu lalu menjalankan pipa grafis. Setiap titik diposisikan oleh [Vertex Shader](/kamus/shader/vertex-shader/), segitiga diubah menjadi kumpulan piksel ([rasterisasi](/kamus/shader/pipeline-raster/)), setiap piksel diwarnai oleh [Fragment Shader](/kamus/shader/fragment-shader/), lalu [Depth Buffer](/kamus/geometri/depth-buffer/) memastikan objek yang dekat menutupi objek yang jauh.

1. **CPU · update:** JavaScript mengubah angka-angka, misalnya rotasi, posisi, warna.
2. **CPU · `renderer.render()`:** Three.js menghitung matriks setiap objek, membuang objek di luar pandangan kamera, mengurutkan objek, lalu mengirim draw call.
3. **GPU · menggambar:** shader dijalankan untuk ribuan titik dan jutaan piksel secara paralel.
4. **Browser · menampilkan:** gambar jadi ditampilkan saat layar melakukan refresh berikutnya.

<Aside type="tip">
Kamu tidak perlu menulis shader untuk membuat scene biasa. Setiap material Three.js, seperti `MeshStandardMaterial`, sudah berisi shader buatan Three.js. Pelajaran shader nanti hanya "membuka kap mesin" itu.
</Aside>

## Bedah kode: persiapan di setup.js

Seluruh persiapan proyek ini ada di satu fungsi. Buka `src/experiment/core/setup.js` di editor dan ikuti nomor barisnya.

```js title="src/experiment/core/setup.js" showLineNumbers startLineNumber=13
export function createSetup(canvas) {
  // Scene: "semesta" yang menampung semua objek, cahaya, dan kamera
  const scene = new THREE.Scene()
  scene.background = new THREE.Color('#0b0b10')
  // Fog membuat objek jauh memudar ke warna latar -> kesan kedalaman
  scene.fog = new THREE.Fog('#0b0b10', 8, 20)

  // PerspectiveCamera(fov, aspect, near, far)
  // - fov: sudut pandang vertikal dalam derajat
  // - aspect: rasio lebar/tinggi; jika salah, gambar akan gepeng/melar
  // - near/far: objek di luar rentang ini tidak digambar (clipping)
  const camera = new THREE.PerspectiveCamera(45, window.innerWidth / window.innerHeight, 0.1, 100)
  camera.position.set(0, 0.6, 6)
  scene.add(camera)

  const renderer = new THREE.WebGLRenderer({ canvas, antialias: true })
  // Bayangan dinyalakan di renderer, lalu per-objek lewat castShadow/receiveShadow
  renderer.shadowMap.enabled = true
  // PCF = tepi bayangan dihaluskan (PCFSoftShadowMap sudah dihapus sejak Three r18x)
  renderer.shadowMap.type = THREE.PCFShadowMap
  // Tone mapping memetakan cahaya HDR ke rentang layar agar highlight tidak "pecah"
  renderer.toneMapping = THREE.ACESFilmicToneMapping
```

- **L15 sampai 16** · Scene dibuat dan diberi warna latar. Warna ini yang terlihat di area yang tidak tertutup objek apa pun.
- **L18** · [Fog](/kamus/cahaya/fog/) `(warna, near, far)`: objek mulai memudar pada jarak 8 unit dari kamera dan hilang total pada jarak 20. Warnanya sengaja sama dengan latar, sehingga ujung lantai "larut" ke latar.
- **L24** · Kamera: fov 45°, aspect diambil dari ukuran jendela, near 0,1, far 100. Jangan membuat rentang antara near dan far terlalu ekstrem (mis. 0.0001 sampai 100000), karena presisi depth buffer akan terbagi ke rentang yang sangat lebar dan permukaan yang berdekatan bisa berkedip (z-fighting).
- **L25** · Kamera mundur 6 unit ke arah +Z (ke arahmu) dan naik 0,6. Objek ada di titik 0,0,0, jadi kamera berada di depannya. Koordinat dibahas di Pelajaran 2.
- **L26** · Menambahkan kamera ke scene sebenarnya opsional. Ini baru diperlukan jika kamera punya anak (misalnya lampu yang menempel di kamera).
- **L28** · Renderer memakai `<canvas>` yang sudah ada di halaman (`src/pages/eksperimen.astro`), bukan membuat kanvas baru. `antialias` menghaluskan tepi bergerigi.
- **L30 sampai 34** · Pengaturan global: bayangan dan [Tone Mapping](/kamus/cahaya/tone-mapping/). Diatur sekali di sini dan berlaku untuk semua objek. Keduanya dibahas di Pelajaran 3.

## Anggaran 16,7 milidetik

Monitor 60 Hz menyegarkan gambarnya 60 kali per detik, berarti 1000 ÷ 60 ≈ **16,7 ms per frame**. Semua pekerjaan dalam satu frame harus selesai dalam anggaran itu: JavaScript, perintah render, dan kerja GPU. Di monitor 144 Hz anggarannya lebih ketat lagi: ±6,9 ms.

<BudgetDiagram />

Jika satu frame butuh 18 ms, gambarnya belum siap saat layar refresh, sehingga layar menampilkan gambar lama sekali lagi. Jika itu terjadi terus-menerus, gambar baru hanya muncul setiap refresh kedua. Akibatnya FPS tidak turun ke 55, tetapi **langsung jatuh ke sekitar 30**. Angka "tepat 30" yang kamu lihat saat laptop memakai baterai berasal dari mekanisme yang sama: browser sengaja hanya mengambil separuh refresh layar untuk menghemat daya.

- **Waktu CPU habis** karena JavaScript yang berat, atau terlalu banyak objek terpisah (setiap objek minimal satu draw call).
- **Waktu GPU habis** karena terlalu banyak piksel ([Pixel Ratio](/kamus/web/pixel-ratio/) tinggi), shader yang berat, atau efek layar penuh (post-processing).
- Panel **Performance** di proyek ini membantu membedakan keduanya. Lihat entri [CPU-bound vs GPU-bound](/kamus/performa/cpu-gpu-bound/) dan [Membaca Panel Performance](/kamus/web/perf-monitor/).

## Render loop

Satu panggilan `renderer.render()` hanya menghasilkan **satu foto diam**. Untuk animasi, fungsi itu harus dipanggil terus, sekali di setiap refresh layar. Alatnya adalah [requestAnimationFrame](/kamus/web/raf/): "browser, panggil fungsi ini tepat sebelum kamu menggambar frame berikutnya".

```js title="src/experiment/main.js" showLineNumbers startLineNumber=66
function tick(timestamp) {
  perf.begin()
  timer.update(timestamp)
  const delta = timer.getDelta()
  const elapsed = timer.getElapsed()

  const { mesh } = objects
  mesh.rotation.y += delta * params.rotationSpeed
  mesh.rotation.x += delta * params.rotationSpeed * 0.4
  // Sinus berosilasi -1..1 -> objek naik-turun seperti mengambang
  mesh.position.y = Math.sin(elapsed * 1.5) * params.floatAmplitude
```

- **L66** · Browser memanggil `tick` dengan `timestamp`, yaitu waktu (milidetik) saat frame ini dimulai.
- **L67** · Mulai mengukur waktu CPU frame ini untuk panel Performance.
- **L68 sampai 70** · `THREE.Timer` mengubah timestamp menjadi dua angka berguna: **delta** (detik sejak frame sebelumnya) dan **elapsed** (detik sejak awal).
- **L73 sampai 74** · Rotasi bertambah sebesar *kecepatan × delta*. Kecepatannya dalam radian per **detik**, bukan per frame. Ini dibahas di bagian berikutnya.
- **L76** · Posisi Y ditentukan langsung dari waktu lewat fungsi sinus, sehingga objek naik-turun. Fungsi sinus dibahas di Pelajaran 2.

```js title="src/experiment/main.js" showLineNumbers startLineNumber=87
  // Render bersyarat: post-processing hanya saat glitch aktif, selebihnya langsung ke layar.
  // Hasil keduanya sama-sama melalui tone mapping + sRGB, jadi warnanya konsisten.
  const usePost = post.isActive()
  if (usePost) post.composer.render(delta)
  else renderer.render(scene, camera)

  perf.end(usePost ? 'composer' : 'direct')
  requestAnimationFrame(tick)
}

requestAnimationFrame(tick)
```

- **L89 sampai 91** · Inilah "jepretan" frame ini. Biasanya `renderer.render()` langsung ke layar. Jalur composer hanya dipakai selama efek glitch (dibahas di pelajaran post-processing).
- **L94** · **Kunci loop:** di akhir frame, `tick` menjadwalkan dirinya sendiri untuk frame berikutnya.
- **L97** · Pemicu pertama. Tanpa baris ini, loop tidak pernah dimulai.

|   | requestAnimationFrame | setInterval(fn, 16) |
| --- | --- | --- |
| Sinkron dengan refresh layar | Ya, dipanggil tepat sebelum layar digambar | Tidak, waktunya meleset sehingga gerakan patah-patah |
| Saat tab tidak terlihat | Berhenti otomatis (hemat baterai) | Tetap berjalan |
| Monitor 120/144 Hz | Otomatis mengikuti | Tetap ±60× per detik |

## Delta time: kecepatan yang adil di semua monitor

Misalkan objek diputar dengan `rotation.y += 0.01` di setiap frame. Di monitor 60 Hz objek bertambah 0,6 radian per detik, tetapi di monitor 144 Hz bertambah 1,44 radian per detik: **2,4 kali lebih cepat**. Animasinya bergantung pada perangkat penonton.

Solusinya [Delta Time](/kamus/dasar/delta-time/): kalikan kecepatan dengan lama frame. Frame di monitor 144 Hz lebih pendek, jadi tambahannya per frame lebih kecil, tetapi totalnya per detik sama. Rumus umumnya: `nilaiBaru = nilaiLama + kecepatanPerDetik × delta`.

<Demo name="delta" caption={"Geser refresh rate. Jarum magenta (per-frame) berubah-ubah, jarum cyan (delta) selalu sama."} />

<Aside type="tip">
**Kapan memakai elapsed, kapan delta?** Elapsed cocok untuk gerakan yang sepenuhnya ditentukan waktu, seperti osilasi sinus. Delta cocok untuk nilai yang *menumpuk* dan kecepatannya bisa berubah di tengah jalan. Coba bayangkan rotasi ditulis `rotation.y = elapsed × speed`, lalu speed diubah lewat GUI: objek akan *melompat* ke sudut baru, karena seluruh riwayat waktu dikalikan dengan speed yang baru.
</Aside>

<Aside type="caution">
Saat tab disembunyikan, requestAnimationFrame berhenti. Ketika tab dibuka lagi, delta bisa bernilai puluhan detik dan objek seolah "teleport". `timer.connect(document)` (main.js baris 64) memakai Page Visibility API untuk mengabaikan jeda tersebut.
</Aside>

## Resize dan pixel ratio

```js title="src/experiment/core/setup.js" showLineNumbers startLineNumber=38
  function resize() {
    sizes.width = window.innerWidth
    sizes.height = window.innerHeight

    // Kamera perlu tahu rasio baru, lalu matriks proyeksinya dihitung ulang
    camera.aspect = sizes.width / sizes.height
    camera.updateProjectionMatrix()

    renderer.setSize(sizes.width, sizes.height)
    renderer.setPixelRatio(Math.min(window.devicePixelRatio, MAX_PIXEL_RATIO))
  }

  resize()
  window.addEventListener('resize', resize)
```

- **L43 sampai 44** · Kamera menyimpan hasil hitungan proyeksinya (matriks proyeksi) dan **tidak** menghitung ulang otomatis karena jarang berubah. Setiap kali `aspect`, `fov`, `near`, atau `far` diubah, `updateProjectionMatrix()` wajib dipanggil.
- **L46** · Mengubah ukuran kanvas. Kanvas punya dua ukuran: **ukuran tampil** (CSS) dan **resolusi gambar** (jumlah piksel yang benar-benar dirender).
- **L47** · Resolusi gambar = ukuran tampil × [Pixel Ratio](/kamus/web/pixel-ratio/). Dibatasi 1,5 agar GPU tidak kewalahan di layar HiDPI.
- **L50 sampai 51** · Dipanggil sekali di awal, lalu setiap kali jendela berubah ukuran.

Pixel ratio sangat berpengaruh karena jumlah piksel naik **kuadratik**: pixel ratio 2 membuat beban 4× lebih berat, bukan 2× (lebar 2× dan tinggi 2×). Setiap piksel tambahan berarti fragment shader dijalankan sekali lagi.

## Kesalahan umum

### Objek tidak bergerak, padahal nilainya berubah

```js title="✗ Keliru"
renderer.render(scene, camera) // dipanggil sekali
setInterval(() => mesh.rotation.y += 0.01, 16)
```

```js title="✓ Benar"
function tick() {
  mesh.rotation.y += delta * speed
  renderer.render(scene, camera)
  requestAnimationFrame(tick)
}
```

Mengubah angka tidak otomatis menggambar ulang. Gambar baru hanya ada jika `render()` dipanggil lagi.

### Gambar gepeng setelah jendela diubah ukurannya

```js title="✗ Keliru"
camera.aspect = innerWidth / innerHeight
```

```js title="✓ Benar"
camera.aspect = innerWidth / innerHeight
camera.updateProjectionMatrix()
```

Matriks proyeksi masih memakai rasio lama sampai dihitung ulang.

### Animasi lebih cepat di monitor gaming

```js title="✗ Keliru"
mesh.rotation.y += 0.01
```

```js title="✓ Benar"
mesh.rotation.y += delta * 0.6 // rad per detik
```

Penambahan per frame bergantung pada berapa banyak frame per detik.

### Lancar di laptop, berat di HP

```js title="✗ Keliru"
renderer.setPixelRatio(window.devicePixelRatio) // HP: 3
```

```js title="✓ Benar"
renderer.setPixelRatio(Math.min(window.devicePixelRatio, 1.5))
```

Pixel ratio 3 berarti 9× jumlah piksel dibanding pixel ratio 1.

### Objek dibuat tetapi tidak muncul (tanpa error)

```js title="✗ Keliru"
const mesh = new THREE.Mesh(geometry, material)
```

```js title="✓ Benar"
const mesh = new THREE.Mesh(geometry, material)
scene.add(mesh)
```

Renderer hanya menggambar yang ada di dalam scene. Three.js tidak memberi peringatan jika objek lupa ditambahkan.

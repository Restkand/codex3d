Empat pelajaran sebelumnya membahas cara membuat aset: [pixel art](/belajar/seni-visual/01-pixel-art/), [sprite dan atlas 2D](/belajar/seni-visual/02-game-2d/), [2.5D](/belajar/seni-visual/03-2-5d/), dan [model 3D](/belajar/seni-visual/04-aset-3d/). Setiap pelajaran itu juga membahas pengaturan impor untuk gayanya sendiri, misalnya filter Point untuk pixel art, atau skala dan sumbu untuk model dari Blender. Pelajaran ini melihat jalurnya secara utuh, dengan fokus pada dua hal yang berlaku untuk semua gaya: cara file berpindah dari aplikasi ke engine, dan berapa memori yang dipakai tekstur setelah sampai di sana.

Jalurnya kira-kira seperti ini:

```text title="Pseudocode: jalur aset dari aplikasi ke GPU"
file sumber   → .aseprite, .kra, .blend: lapisan, riwayat, pengaturan
ekspor        → .png, .json, .glb/.gltf: hasil rata yang dibaca engine
impor         → engine membaca file ekspor dan pengaturan impornya
format GPU    → engine mengubah piksel ke format yang dibaca GPU
memori GPU    → lebar × tinggi × byte per piksel, ditambah mipmap
```

Dua baris terakhir sering terlewat. GPU tidak membaca file PNG di folder proyek. Engine mengubahnya ke format lain saat impor atau saat game dimuat, dan format itulah yang menentukan memori dan kualitas di perangkat pemain.

## File sumber dan file ekspor

**File sumber** adalah file kerja di aplikasi pembuatnya. File ini menyimpan semua yang dibutuhkan untuk mengubah aset nanti: lapisan, tag animasi, modifier, riwayat, dan pengaturan. **File ekspor** adalah hasil rata yang dibaca engine.

| Aplikasi | File sumber | Isi yang hanya ada di file sumber | File ekspor umum |
| --- | --- | --- | --- |
| Aseprite | `.aseprite` / `.ase` | Lapisan, tag animasi, slice, palet | `.png` sprite sheet + `.json` |
| Krita | `.kra` | Lapisan, mask, filter layer, ruang warna per lapisan | `.png` |
| Blender | `.blend` | Modifier, high poly, kamera, lampu, pengaturan ekspor | `.glb` atau `.gltf` + `.bin` + tekstur |

Manual Krita menyebut `.kra` sebagai format internal yang menyimpan semua fitur yang bisa ditangani Krita, dan sebagian besar aplikasi lain tidak bisa membukanya. Isinya adalah arsip yang bisa dibuka sebagai `.zip`, dan di dalamnya ada `mergedimage.png` berisi gambar rata seperti yang tampil di kanvas. Hal serupa berlaku untuk dua aplikasi lain: file ekspor kehilangan lapisan dan pengaturan yang membuat aset bisa diubah dengan mudah.

Aturan dasarnya:

- **File sumber adalah sumber kebenaran.** Semua perubahan dimulai dari file sumber, lalu diekspor ulang. PNG hasil ekspor tidak diedit langsung.
- **File sumber disimpan dan dicadangkan.** File ini besar dan biner, jadi biasanya dilacak dengan Git LFS atau sistem lain yang dibahas di [Pelajaran 4 Produksi](/belajar/produksi/04-alat-kerja/#git-dan-git-lfs).
- **File ekspor bisa dibuat ulang.** Kalau file ekspor hilang, kamu cukup mengekspor lagi. Kalau file sumber hilang, kamu hanya punya hasil akhir.

### Engine yang membaca file sumber langsung

Beberapa engine bisa mengimpor file sumber tanpa langkah ekspor:

- **Unity** meratakan file PSD dan TIFF berlapis saat impor, tanpa mengubah file aslinya, sehingga satu file bisa dipakai di aplikasi gambar dan di Unity sekaligus. Paket **2D Aseprite Importer** mengimpor file `.ase` dan `.aseprite`. Menurut dokumentasi paket versi 1.1, paket ini sudah terpasang saat membuat proyek 2D atau 2D URP baru di Unity 2021.3.28f1, 2022.3.2f1, atau versi yang lebih baru.
- **Godot** dan **Unity** bisa mengimpor `.blend` jika Blender terpasang di komputer setiap anggota tim, seperti dibahas di [Pelajaran 4](/belajar/seni-visual/04-aset-3d/#format).

Cara ini menghemat satu langkah, dengan harga yang perlu dipertimbangkan: setiap orang yang membuka proyek butuh aplikasi yang sama, hasil impor bisa bergantung pada versi aplikasi itu, dan file sumber yang besar ikut masuk ke folder proyek engine. Banyak tim memakai impor langsung untuk aset yang sering berubah selama prototipe, lalu beralih ke file ekspor saat produksi berjalan. Keduanya sah, asal tim memilih satu cara per jenis aset dan menuliskannya.

## Penamaan dan susunan folder

Nama dan folder menentukan apakah orang lain bisa menemukan aset, dan apakah ekspor ulang menimpa file yang benar. Aturan penamaan umum untuk aset 3D, termasuk akhiran yang dibaca importer, sudah dibahas di [Pelajaran 4](/belajar/seni-visual/04-aset-3d/#penamaan-dan-susunan-file). Bagian ini menambahkan hubungan antara file sumber dan file ekspor.

**Satu file sumber, satu nama dasar.** File ekspor memakai nama dasar yang sama dengan file sumbernya, supaya asal setiap file jelas:

```text title="Contoh: susunan folder dengan sumber terpisah dari proyek engine"
proyek-game/
  sumber/                         ← file kerja, dilacak Git LFS
    karakter/pedagang/pedagang.aseprite
    prop/tong_kayu/tong_kayu.blend
    prop/tong_kayu/tong_kayu_basecolor.kra
  game/                           ← folder proyek engine
    karakter/pedagang/pedagang.png
    karakter/pedagang/pedagang.json
    prop/tong_kayu/tong_kayu.gltf
    prop/tong_kayu/tong_kayu.bin
    prop/tong_kayu/tong_kayu_basecolor.png
```

**Huruf kecil dan tanpa spasi.** Dokumentasi Godot menyarankan `snake_case` untuk nama folder dan file, karena Windows dan macOS umumnya tidak membedakan huruf besar-kecil, sedangkan sistem file virtual PCK di game Godot yang sudah diekspor membedakannya. File bernama `Tong.png` yang dipanggil sebagai `tong.png` bisa berjalan di editor lalu gagal di build. Tim yang memakai pola lain, misalnya awalan `T_` dan `SM_` seperti di Pelajaran 4, tetap aman asal penulisannya konsisten.

**Simpan file sumber di tempat yang tidak diimpor engine.** Unity mengimpor file gambar di dalam folder `Assets`, dan Godot mengimpor semua file yang bisa diimpornya di folder proyek. File sumber yang ikut terimpor menambah waktu impor dan bisa ikut terbawa ke build. Dua pilihan yang umum:

- Taruh folder `sumber/` di luar folder proyek engine, seperti contoh di atas.
- Di Godot, folder di dalam proyek bisa diabaikan dengan file kosong bernama `.gdignore`. Menurut dokumentasi Godot, folder itu tidak diimpor, tidak tampil di dock FileSystem, dan isinya tidak ikut diekspor bersama proyek.

## Ekspor dari Aseprite

Untuk animasi dan sprite, Aseprite mengekspor dua file: gambar sprite sheet, dan data JSON yang menjelaskan letak setiap frame di gambar itu. Cara kerja [sprite sheet](/kamus/2d/sprite-sheet/) dan [atlas](/kamus/2d/sprite-atlas/) di engine dibahas di [Pelajaran 2](/belajar/seni-visual/02-game-2d/#sprite-sheet-atlas-dan-packing).

**Lewat antarmuka.** Menu **File → Export Sprite Sheet** membuka dialog ekspor. Menurut dokumentasi Aseprite, kamu bisa memilih semua lapisan yang terlihat atau satu lapisan saja, dan memilih frame berdasarkan tag.

**Lewat baris perintah.** Aseprite punya antarmuka baris perintah (CLI) yang menjalankan ekspor yang sama tanpa membuka jendela program. Opsi `-b` (`--batch`) menjalankan Aseprite hanya untuk memproses perintah lalu selesai, dan dokumentasinya menyebut opsi ini berguna untuk mengotomatiskan pembuatan sprite sheet dari skrip.

```bash title="Mengekspor sprite sheet dan data JSON lewat CLI Aseprite"
aseprite -b --list-tags sumber/karakter/pedagang/pedagang.aseprite \
  --sheet-type rows --shape-padding 2 \
  --sheet game/karakter/pedagang/pedagang.png \
  --data game/karakter/pedagang/pedagang.json \
  --format json-array
```

Arti setiap opsi, menurut dokumentasi CLI Aseprite:

- `--sheet` menyimpan semua gambar yang disebut sebelum opsi ini ke satu file sprite sheet. File yang sudah ada akan ditimpa.
- `--data` menyimpan informasi sprite sheet dalam format JSON. `--format` memilih `json-hash` (bawaan) atau `json-array`.
- `--list-tags` memasukkan daftar tag animasi ke bagian `meta` di JSON, lengkap dengan frame awal dan akhirnya. Opsi ini ditulis sebelum nama file yang dimaksud.
- `--sheet-type` memilih susunan: `horizontal`, `vertical`, `rows`, `columns`, atau `packed`. `--sheet-pack` memakai algoritme pengemasan untuk menghindari ruang kosong.
- `--shape-padding` memberi jarak antar-frame dalam piksel, `--border-padding` memberi bingkai di sekeliling sheet, dan `--inner-padding` memberi bingkai di setiap frame.
- `--sheet-width` dan `--sheet-height` menetapkan ukuran sheet dalam piksel.

Contoh keluaran yang ditautkan dari dokumentasi CLI menunjukkan isi setiap frame di JSON: posisi dan ukuran potongan di sheet (`frame`), ukuran asli sebelum di-trim (`sourceSize`), dan durasi frame (`duration`).

**Siapa yang membaca JSON itu.** Format JSON ini milik Aseprite, jadi engine tidak otomatis memahaminya. Unity punya 2D Aseprite Importer yang membaca file `.aseprite` langsung, sehingga JSON tidak dibutuhkan di jalur itu. Di engine lain, JSON dibaca oleh plugin importer atau skrip buatan tim, yang memotong sheet menjadi frame dan membuat animasi dari tag. Kalau tidak ada yang membaca JSON, kamu harus memotong sheet secara manual di engine, dan setiap perubahan susunan frame berarti memotong ulang.

## Ekspor dari Krita

Krita sering dipakai untuk melukis tekstur, ilustrasi latar, karakter 2D beresolusi tinggi, dan elemen UI.

**Save dan Export.** **File → Save** menyimpan `.kra` dengan semua lapisannya. Menurut manual Krita, **File → Export…** menyimpan salinan ke lokasi lain tanpa membukanya sebagai dokumen aktif, sehingga kamu bisa terus bekerja di file berlapis dan hanya mengirim versi rata ke engine. **Export Advanced…** menambahkan pilihan memotong dan mengubah ukuran saat ekspor.

**PNG untuk engine.** Manual Krita menjelaskan PNG sebagai format lossless yang menyimpan semua warna gambar dengan tepat dan mendukung transparansi alpha penuh. Ini cocok untuk engine, karena kompresi untuk GPU dilakukan oleh engine sendiri saat impor. Satu catatan dari dokumentasi Godot: presisi PNG dibatasi 8 bit per channel saat diimpor ke Godot, jadi mengekspor PNG 16 bit untuk tekstur biasa tidak menambah apa pun di sana.

**Banyak lapisan menjadi banyak file.** Untuk sprite atau UI yang dilukis dalam satu dokumen dengan banyak lapisan, Krita menyertakan plugin Python bawaan:

- **Batch Exporter**, yang menurut manual Krita ditujukan untuk game developer dan desainer grafis. Plugin ini mengekspor aset ke beberapa ukuran, jenis file, dan lokasi sekaligus, bisa mengekspor semua lapisan atau lapisan terpilih, dan secara bawaan menaruh hasilnya di folder ekspor di sebelah dokumen Krita dengan susunan mengikuti tumpukan lapisan.
- **Export Layers**, yang mengekspor lapisan dokumen secara berurutan.

**Ruang warna.** Bagian *Games* di halaman alur kerja warna manual Krita menyarankan ruang kerja sRGB, atau grayscale linear untuk roughness dan specular map, dan gambar yang dikirim ke engine dalam sRGB atau grayscale. Untuk normal map, height map, dan peta data seperti metalness dan roughness, manual itu menyarankan agar engine diberi tahu bahwa gambar tersebut linear, atau setidaknya tidak dikonversi. Pengaturannya di engine dijelaskan di Kamus [Color Space](/kamus/cahaya/color-space/) dan di tabel tekstur PBR [Pelajaran 4](/belajar/seni-visual/04-aset-3d/#tekstur-pbr).

## Ekspor dari Blender

Persiapan model sebelum ekspor (satuan, apply transform, sumbu, normal, triangulasi) dan pengaturan importer model di setiap engine sudah dibahas di [Pelajaran 4](/belajar/seni-visual/04-aset-3d/#ekspor-dan-impor). Bagian ini membahas pilihan file dan tekstur di eksporter glTF.

**Tiga bentuk file glTF.** Manual Blender menjelaskan tiga pilihan **Format**:

| Format | Isi | Kapan dipakai |
| --- | --- | --- |
| **glTF Binary** (`.glb`) | Satu file biner berisi mesh, tekstur, dan data lain | Mudah dibagikan atau disalin sebagai satu file |
| **glTF Separate** (`.gltf` + `.bin` + tekstur) | File teks JSON untuk struktur, `.bin` untuk data mesh, dan file gambar terpisah | Lebih mudah mengedit JSON atau gambar setelah ekspor, tetapi semua file harus dibagikan bersama |
| **glTF Embedded** (`.gltf`) | Satu file teks dengan data biner dikodekan Base64 | Menurut manual, bentuk paling tidak efisien. Hanya muncul jika diaktifkan di preferensi add-on |

Untuk glTF Separate, opsi **Textures** menentukan folder tempat file tekstur ditulis, relatif terhadap file `.gltf`. Bentuk ini membuat tekstur menjadi file sendiri di proyek engine, sehingga setiap tekstur bisa diberi pengaturan impor sendiri dan diganti tanpa mengekspor ulang mesh.

**Format gambar.** Manual Blender mencatat bahwa glTF mensyaratkan tekstur material dalam format PNG atau JPEG, dan add-on mengonversi format lain secara otomatis. Opsi **Images** memilih format keluaran: PNG lossless dan umumnya lebih disukai, JPEG menghasilkan file lebih kecil, WebP menyimpan semua tekstur sebagai WebP tanpa cadangan PNG atau JPEG, dan **None** mengekspor material tanpa tekstur. Seperti PNG dari Krita, format file di sini hanya memengaruhi ukuran di disk dan kualitas sumber. Memori di GPU ditentukan pengaturan impor engine.

**Menyimpan pengaturan ekspor.** Dua fitur Blender membuat ekspor bisa diulang dengan pengaturan yang sama:

- **Remember Export Settings** menyimpan pengaturan ekspor di file `.blend`, sehingga pengaturan itu muncul lagi saat file dibuka berikutnya.
- **Collection Exporters**: setiap collection bisa diberi satu atau beberapa eksporter, termasuk glTF 2.0 dan FBX. Manual Blender menyebut panel ini menyederhanakan ekspor ulang aset yang sama berulang kali, misalnya saat membuat aset glTF untuk game. Tombol **Export All** mengekspor semua eksporter di collection aktif, dan **File → Export All Collections** mengekspor semuanya sekaligus.

## Ekspor ulang tanpa kejutan

Aset jarang selesai dalam satu kali ekspor. Warna diubah, frame ditambah, segitiga dikurangi. Setiap perubahan berarti ekspor ulang, dan di sinilah banyak masalah kecil muncul: jarak antar-frame berbeda dari ekspor sebelumnya, lapisan sketsa ikut terekspor, atau nama file berubah sehingga engine menganggapnya aset baru.

Ekspor yang **bisa diulang** berarti siapa pun yang menjalankan langkah yang sama dari file sumber yang sama akan mendapat file ekspor yang sama. Ini penting karena tiga alasan:

- **Orang lain bisa melanjutkan.** Kalau artist yang membuat aset sedang tidak ada, anggota tim lain tetap bisa memperbaiki dan mengekspor tanpa menebak pengaturannya.
- **Perubahan bisa dilacak.** Kalau hasil di engine berubah, kamu tahu penyebabnya ada di file sumber, karena langkah ekspornya tetap.
- **Ekspor massal menjadi mungkin.** Mengganti padding untuk seratus sprite sheet cukup dengan mengubah satu skrip, lalu menjalankannya lagi.

### Di sisi aplikasi

| Aplikasi | Cara menyimpan langkah ekspor |
| --- | --- |
| Aseprite | Perintah CLI dengan `-b` di file skrip yang disimpan di repositori |
| Krita | Batch Exporter dengan lokasi dan ukuran yang tetap |
| Blender | Collection Exporters dan Remember Export Settings, tersimpan di file `.blend` |

### Di sisi engine

Engine menyimpan pengaturan impor di file pendamping, di sebelah file ekspor:

- **Unity** membuat file `.meta` untuk setiap aset di folder `Assets`. Menurut dokumentasi Unity, file ini menyimpan ID unik aset dan semua pengaturan impornya. Kalau sebuah tekstur kehilangan `.meta`-nya, material yang memakainya kehilangan referensi ke tekstur itu dan harus diisi ulang manual. Memindahkan atau mengganti nama aset di luar Unity berarti file `.meta` harus ikut dipindahkan.
- **Godot** membuat file `<nama aset>.import` di sebelah file sumber, berisi konfigurasi impor. Dokumentasi Godot meminta file ini ikut di-commit ke version control. Saat checksum MD5 file berubah, Godot mengimpor ulang aset secara otomatis dengan pengaturan yang sama. Hasil impornya disimpan di folder tersembunyi `res://.godot/imported/`, yang tidak disarankan untuk di-commit.

Akibatnya untuk alur ekspor ulang: **timpa file lama dengan nama dan lokasi yang sama.** Engine akan mendeteksi perubahan, mengimpor ulang dengan pengaturan yang tersimpan, dan semua referensi tetap utuh. Mengekspor ke nama baru seperti `pedagang_final2.png` lalu menghapus yang lama membuang pengaturan impor dan memutus referensi.

**Pengaturan bawaan per jenis aset.** Supaya aset baru langsung mendapat pengaturan yang benar, kedua engine menyediakan cara mengatur nilai bawaan. Unity punya **Presets**, yang menurut dokumentasinya bisa dipakai sebagai pengaturan impor bawaan dan diterapkan berdasarkan lokasi folder aset. Godot punya menu **Preset…** di dock Import dan tab **Import Defaults** di Project Settings untuk mengubah nilai bawaan per jenis aset.

## Menghitung memori tekstur

Memori sebuah tekstur di GPU bisa dihitung sebelum aset dibuat. Rumusnya sederhana:

```text title="Pseudocode: memori satu tekstur di GPU"
byte_per_piksel = bit_per_piksel_format / 8
memori          = lebar × tinggi × byte_per_piksel
jika mipmap:      memori = memori × 4/3        // sekitar +33%
```

Angka `4/3` datang dari rantai mipmap. Setiap tingkat berukuran separuh di kedua sisi, jadi luasnya seperempat tingkat sebelumnya: 1 + 1/4 + 1/16 + 1/64 + … mendekati 4/3. Dokumentasi Unity dan Godot sama-sama menyebut mipmap menambah sekitar 33% memori. Penjelasan cara kerja mipmap ada di Kamus [Texture Filtering & Mipmap](/kamus/geometri/texture-filtering/#mipmap).

### Bit per piksel setiap format

Yang berubah dari satu format ke format lain adalah bit per piksel. Tabel format GPU di dokumentasi Unity mencantumkan angkanya:

| Format | Channel | Bit per piksel | Ukuran 1024 × 1024 (tabel Unity) |
| --- | --- | --- | --- |
| RGBA 32 bit (tanpa kompresi) | RGBA | 32 | 4 MB |
| RGB 24 bit (tanpa kompresi) | RGB | 24 di disk, 32 di GPU | 3 MB di disk, 4 MB di GPU |
| R 8 (tanpa kompresi) | R | 8 | 1 MB |
| BC7 | RGB atau RGBA | 8 | 1 MB |
| DXT1 (BC1) | RGB | 4 | 0,5 MB |
| BC4 | R | 4 | 0,5 MB |
| BC5 | RG | 8 | 1 MB |
| ETC2 RGBA | RGBA | 8 | 1 MB |
| ASTC 4x4 | RGB atau RGBA | 8 | 1,0 MB |
| ASTC 6x6 | RGB atau RGBA | 3,56 | 0,45 MB |
| ASTC 8x8 | RGB atau RGBA | 2 | 0,25 MB |

Dua hal dari tabel ini sering mengejutkan. Pertama, tekstur RGB tanpa alpha tetap memakan 4 byte per piksel di GPU, karena diubah ke RGBA 32 bit. Kedua, format terkompresi berbeda jauh satu sama lain: DXT1 memakai seperdelapan memori RGBA 32 bit, sedangkan BC7 seperempatnya dengan kualitas lebih tinggi.

Dokumentasi Godot memberi tabel serupa untuk satu tekstur RGBA8 dengan mipmap: 1024 × 1024 memakan 5,33 MiB dengan Lossless dan 1,33 MiB dengan VRAM Compressed, sedangkan 2048 × 2048 memakan 21,33 MiB dan 5,33 MiB. Dokumentasi itu juga mencatat bahwa dengan rasio kompresi 4:1, VRAM Compressed praktis memungkinkan tekstur dua kali lebih besar di setiap sumbu dengan memori GPU yang sama.

Tabel Unity menulis satuan MB. Hitungan di pelajaran ini memakai MiB (1 MiB = 1024 × 1024 byte) supaya angkanya bulat, dan untuk tekstur berukuran pangkat dua angkanya sama dengan tabel Unity.

### Ukuran di disk tidak sama dengan memori

File PNG 2048 × 2048 di disk bisa berukuran beberapa ratus KB saja, karena PNG mengompresi gambar tanpa kehilangan data. GPU tidak membaca PNG. Saat dimuat, gambar dibuka menjadi piksel mentah atau diubah ke format GPU, dan memorinya mengikuti tabel di atas. Ada beberapa pengaturan yang hanya memperkecil ukuran di disk:

- **Lossy** di Godot memperkecil file, tetapi memori video tetap sama dengan Lossless.
- **Crunch** di Unity memperkecil ukuran di disk, tetapi tidak berpengaruh pada memori saat game berjalan.

Sebaliknya, ada situasi yang menambah memori melebihi hitungan. Dokumentasi Unity menyebut tekstur dengan format yang tidak didukung perangkat akan didekompresi ke format tanpa kompresi, dan salinan itu disimpan di memori bersama tekstur aslinya. **Read/Write** yang aktif juga menggandakan memori tekstur di Unity.

### Kompresi juga soal kecepatan

Dokumentasi Unity menjelaskan bahwa bit per piksel yang lebih rendah juga berarti GPU memakai lebih sedikit bandwidth memori untuk membaca tekstur, dan bandwidth memori sering menjadi penghambat frame rate. Dokumentasi Godot menyebut hal yang sama, terutama untuk grafis terintegrasi dan ponsel. Karena itu, tekstur terkompresi bisa membuat game berjalan lebih cepat, selain lebih hemat memori.

Harganya adalah kualitas. Dokumentasi Unity menyebut semua format kompresi tekstur bersifat lossy sampai tingkat tertentu. Untuk foto dan tekstur 3D biasanya tidak terlihat, tetapi untuk pixel art dan UI yang harus tajam per piksel, kompresi sering merusak tampilan, seperti dibahas di [Pelajaran 1](/belajar/seni-visual/01-pixel-art/#kompresi).

## Ukuran pangkat dua

Ukuran pangkat dua adalah 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048, dan seterusnya. Lebar dan tinggi tidak harus sama: 1024 × 512 juga pangkat dua di kedua sisi.

Apa kata dokumentasi engine:

- **Unity** menyebut ukuran ideal adalah pangkat dua di setiap sisi. Tekstur yang bukan pangkat dua (NPOT) umumnya memakai sedikit lebih banyak memori dan bisa lebih lambat dibaca GPU. Jika platform atau GPU tidak mendukung NPOT, Unity menskalakan dan menambal tekstur ke pangkat dua berikutnya, yang menambah memori dan memperlambat pemuatan. Untuk membuat mipmap otomatis, Unity mensyaratkan resolusi tekstur berupa pangkat dua. Dokumentasinya juga menyarankan NPOT hanya untuk GUI.
- **Godot** menyebut ukuran pangkat dua disarankan tetapi tidak wajib, dan tekstur tidak harus persegi.
- **Format PVRTC** di Unity mensyaratkan tekstur persegi. Contoh di dokumentasi Unity: tekstur 257 × 511 yang diskalakan **To nearest** menjadi 256 × 512, lalu diperbesar lagi ke 512 × 512 jika memakai PVRTC.

Alasannya terlihat dari rantai mipmap. Tekstur 1024 dibagi dua terus menjadi 512, 256, 128, sampai 1, dan setiap tingkat tetap bilangan bulat. Dokumentasi Godot memberi contoh: tekstur 64 × 64 menghasilkan 6 tingkat mipmap (32, 16, 8, 4, 2, 1). Tekstur 1000 × 1000 dibagi dua menjadi 500, 250, 125, lalu 62,5, yang harus dibulatkan, sehingga setiap tingkat tidak lagi tepat separuh tingkat sebelumnya.

Untuk artist, keputusan ini paling murah diambil di file sumber. Kanvas Krita atau ukuran bake di Blender yang langsung pangkat dua menghasilkan file ekspor yang benar di semua engine, tanpa bergantung pada opsi penskalaan di importer. Untuk sprite sheet, ukuran akhirnya ditentukan oleh jumlah frame dan padding, jadi hitung dulu, atau tetapkan ukuran sheet saat ekspor dengan `--sheet-width` dan `--sheet-height` di Aseprite.

## Ilustrasi: dari aplikasi ke engine

<Aside type="caution" title="Ilustrasi, bukan data">
Aset, ukuran, dan keputusan di bagian ini adalah contoh. Bit per piksel diambil dari tabel format Unity dan Godot. Hasil sebenarnya bergantung pada format yang dipilih engine untuk platform target, jadi selalu periksa di engine.
</Aside>

### Sprite sheet karakter pixel art

Karakter pedagang digambar di Aseprite dengan frame 32 × 32 piksel. Ada tiga tag: `diam` (4 frame), `jalan` (8 frame), dan `serang` (6 frame), total 18 frame.

```text title="Ilustrasi: dua cara mengekspor 18 frame 32 × 32"
horizontal, tanpa padding
  lebar  = 18 × 32 = 576, tinggi = 32
  memori = 576 × 32 × 4 byte = 73.728 byte = 72 KiB   (Lossless, tanpa mipmap)
  catatan: 576 bukan pangkat dua

dikemas ke 256 × 256 (--sheet-pack --sheet-width 256 --sheet-height 256)
  memori = 256 × 256 × 4 byte = 262.144 byte = 256 KiB
  catatan: pangkat dua, masih ada ruang untuk frame tambahan
```

Keduanya kecil, jadi untuk pixel art keputusan ini jarang soal memori. Pilihan horizontal lebih hemat di sini, tetapi strip yang terus memanjang punya batas: bos 64 × 64 dengan 80 frame dalam satu baris lebarnya 5.120 piksel, melewati batas 4096 yang menurut dokumentasi Godot biasanya berlaku di ponsel dan web. Sheet yang dikemas ke ukuran tetap menghindari masalah itu dan memenuhi saran pangkat dua di Unity.

Di engine, sheet ini diimpor dengan pengaturan pixel art dari [Pelajaran 1](/belajar/seni-visual/01-pixel-art/#menyiapkan-proyek-di-tiap-engine): filter Point atau Nearest, tanpa mipmap, tanpa kompresi. Kompresi ditolak dengan sengaja: hematnya hanya beberapa ratus KiB, sedangkan warnanya bisa keluar dari palet. Kalau sheet ini kemudian digabung ke sprite atlas bersama aset lain, pengaturan atlas yang berlaku, seperti dijelaskan di [Pelajaran 2](/belajar/seni-visual/02-game-2d/#pengaruhnya-ke-memori).

### Tekstur prop 3D

Tong kayu dimodelkan di Blender. Normal map dan ORM di-bake di Blender, base color dilukis di Krita. Ketiga tekstur berukuran 2048 × 2048, dan model diekspor sebagai glTF Separate supaya setiap tekstur menjadi file sendiri di engine. Semua tekstur memakai mipmap.

```text title="Ilustrasi: memori tiga tekstur 2048 × 2048 dengan mipmap"
tanpa kompresi (RGBA 32 bit, 4 byte per piksel)
  per tekstur  = 2048 × 2048 × 4 = 16 MiB, × 4/3 ≈ 21,33 MiB
  tiga tekstur ≈ 64 MiB

desktop, kompresi bawaan Godot (S3TC, High Quality mati)
  base color   DXT1, 4 bit  → 2048 × 2048 × 0,5 = 2 MiB, × 4/3 ≈ 2,67 MiB
  normal map   RGTC, memori setara RGBA terkompresi (tabel Godot) ≈ 5,33 MiB
  ORM          DXT1, 4 bit  ≈ 2,67 MiB
  total        ≈ 10,67 MiB

ponsel, anggap ketiganya ASTC 6x6 (Normal Quality di Unity untuk Android dan iOS)
  per tekstur  = 2048 × 2048 × 3,56 / 8 ≈ 1,78 MiB, × 4/3 ≈ 2,37 MiB
  tiga tekstur ≈ 7,1 MiB
```

Kompresi membuat memori turun dari sekitar 64 MiB ke sekitar 7 sampai 11 MiB untuk satu prop. Tong ini lalu diuji di perangkat target, dan ternyata hanya tampil kecil di layar. Tim memutuskan memakai Max Size 1024 di tab Android (Unity) atau Size Limit 1024 (Godot):

```text title="Ilustrasi: tekstur yang sama setelah dibatasi ke 1024 × 1024"
ASTC 6x6, 1024 × 1024 → 0,45 MiB (tabel Unity), × 4/3 ≈ 0,59 MiB
tiga tekstur          ≈ 1,8 MiB
```

Setiap kali sisi tekstur dibagi dua, memorinya menjadi seperempat. File sumber tetap 2048, jadi kalau nanti ada platform dengan memori lebih besar, tekstur resolusi penuh masih tersedia tanpa melukis ulang. Cara menentukan ukuran tekstur dari texel density dan ukuran objek ada di [Pelajaran 4](/belajar/seni-visual/04-aset-3d/#uv-unwrapping-dan-texel-density).

### PNG hasil ekspor dijadikan file kerja

```text title="✗ Keliru"
pedagang.png diedit langsung di aplikasi gambar, lalu disimpan
pedagang.aseprite tidak diperbarui
ekspor berikutnya dari .aseprite menimpa perbaikan di PNG
```

```text title="✓ Benar"
semua perubahan di pedagang.aseprite
ekspor ulang ke pedagang.png dan pedagang.json
```

File ekspor tidak punya lapisan, tag, atau riwayat. Perbaikan yang hanya ada di file ekspor akan hilang di ekspor berikutnya.

### Ekspor ulang dengan nama baru

```text title="✗ Keliru"
ekspor ke tong_kayu_v2.png, hapus tong_kayu.png di file explorer
material kehilangan tekstur, pengaturan impor kembali ke bawaan
```

```text title="✓ Benar"
ekspor ulang ke tong_kayu.png di lokasi yang sama (timpa)
versi lama disimpan di riwayat version control, tidak di nama file
```

File `.meta` di Unity dan `.import` di Godot terikat pada nama dan lokasi file. Nama baru berarti aset baru.

### Mengukur beban tekstur dari ukuran file di disk

```text title="✗ Keliru"
"teksturnya cuma 600 KB di folder, jadi ringan"
```

```text title="✓ Benar"
memori = lebar × tinggi × byte per piksel format GPU, × 4/3 jika mipmap
2048 × 2048 tanpa kompresi ≈ 21,33 MiB, berapa pun ukuran PNG-nya
```

Ukuran PNG mencerminkan seberapa mudah gambar dikompresi tanpa kehilangan data. GPU memakai format lain.

### Mipmap aktif untuk tekstur yang tidak pernah mengecil

```text title="✗ Keliru"
ikon dan panel UI yang selalu tampil seukuran aslinya, mipmap aktif
```

```text title="✓ Benar"
mipmap mati untuk UI yang tidak diskalakan dan sprite 2D yang tidak di-zoom out
mipmap aktif untuk tekstur 3D dan sprite yang bisa tampil mengecil
```

Mipmap menambah sekitar 33% memori. Manfaatnya hanya muncul saat tekstur tampil lebih kecil dari ukuran aslinya.

### Satu pengaturan kompresi untuk semua tekstur

```text title="✗ Keliru"
semua tekstur proyek: VRAM Compressed (Godot) atau Normal Quality (Unity)
termasuk pixel art, teks di UI, dan tekstur data
```

```text title="✓ Benar"
tekstur 3D warna dan data: kompresi GPU, sRGB sesuai isinya
normal map: mode normal map engine (RGTC di Godot)
pixel art dan UI tajam: tanpa kompresi
atur bawaan per folder: Presets (Unity), Import Defaults (Godot)
```

Jenis tekstur yang berbeda butuh format yang berbeda. Pengaturan bawaan per folder atau per jenis aset mencegah tekstur baru masuk dengan pengaturan yang salah.

### Mengekspor sebesar mungkin untuk berjaga-jaga

```text title="✗ Keliru"
semua tekstur diekspor 4096 × 4096, "nanti bisa dikecilkan"
tidak ada yang mengatur Max Size atau Size Limit
```

```text title="✓ Benar"
file sumber boleh beresolusi tinggi
ukuran di engine ditetapkan dari texel density dan perangkat target
Max Size per platform (Unity), Size Limit (Godot)
```

Satu tekstur 4096 × 4096 tanpa kompresi dengan mipmap memakan sekitar 85,33 MiB menurut tabel Godot. Simpan resolusi tinggi di file sumber, dan batasi di engine.

## Latihan

Kerjakan dengan aset buatanmu sendiri atau aset berlisensi jelas, di Unity atau Godot.

1. **Susunan proyek.** Buat folder `sumber/` dan folder proyek engine seperti contoh di bagian [penamaan dan susunan folder](#penamaan-dan-susunan-folder). Tulis aturan nama file di satu halaman catatan proyek, termasuk huruf besar-kecil dan akhiran tekstur.
2. **Ekspor Aseprite lewat skrip.** Buat animasi pendek dengan dua tag di Aseprite. Tulis perintah CLI yang mengekspor sprite sheet dan JSON ke folder proyek engine, simpan perintah itu di file skrip, lalu jalankan dua kali. Bandingkan kedua hasilnya. Ubah satu frame, jalankan lagi, dan pastikan engine mengimpor ulang tanpa kehilangan pengaturan.
3. **Ekspor ulang glTF.** Di Blender, tambahkan Collection Exporter glTF 2.0 dengan format glTF Separate ke collection berisi satu prop. Ekspor, impor ke engine, dan beri tekstur pengaturan impor yang berbeda dari bawaan. Ubah warna di Blender, klik **Export All**, lalu periksa apakah pengaturan impor tekstur masih sama.
4. **Hitung lalu periksa.** Pilih tiga tekstur di proyekmu. Untuk setiap tekstur, hitung memorinya dengan rumus di bagian [menghitung memori tekstur](#menghitung-memori-tekstur), sekali tanpa kompresi dan sekali dengan format yang dipilih engine. Di Godot, bandingkan dengan angka memori di Inspector. Di Unity, catat Format di tab platform, lalu cocokkan dengan tabel bit per piksel.
5. **Anggaran tekstur satu scene.** Daftar semua tekstur di satu scene uji beserta ukurannya. Hitung total memori tanpa kompresi dan dengan kompresi untuk desktop dan ponsel. Tandai tekstur yang bisa dikecilkan dengan Max Size atau Size Limit tanpa perbedaan yang terlihat di perangkat target.

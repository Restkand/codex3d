## Gambaran besar

<Aside type="note" title="Model mental: gedung pertunjukan">
Sebuah pertunjukan butuh panggung, lampu, pengeras suara, dan jadwal yang menentukan kapan setiap pemain masuk. Di belakangnya ada ruang latihan untuk menyusun adegan, gudang tempat kostum dan properti disiapkan, dan truk yang membawa pertunjukan ke kota lain. Engine game menyediakan semuanya. Kamu menulis naskahnya dan menyiapkan propertinya.
</Aside>

Engine game adalah perangkat lunak yang berisi dua hal. Yang pertama adalah **runtime**, program yang menjalankan game di perangkat pemain. Dalam analogi tadi, runtime adalah panggung beserta jadwalnya. Yang kedua adalah **alat produksi**: editor sebagai ruang latihan, pipeline aset sebagai gudang, dan pembuat build sebagai truknya.

Pelajaran-pelajaran di [Fondasi Engine](/belajar/fondasi-engine/) membahas isi runtime, dari game loop sampai profiling. Pelajaran ini mundur selangkah dan melihat engine sebagai satu paket utuh. Dengan begitu, engine yang berbeda bisa dibandingkan memakai ukuran yang sama, dan dokumentasi engine yang belum pernah kamu pakai bisa dibaca dengan peta yang sudah kamu kenal.

## Library, framework, dan engine

Ketiga istilah ini sering dipakai bergantian. Cara tercepat membedakannya adalah bertanya: **siapa yang memegang game loop?**

**Library** adalah kumpulan fungsi yang kamu panggil. Game loop kamu tulis sendiri, lalu library dipakai di dalamnya untuk pekerjaan tertentu, misalnya membuka jendela atau menggambar sprite.

```text title="Pseudocode: memakai library"
buka_jendela(1280, 720)              // fungsi dari library

selama game berjalan:                // loop ini milikmu
    tombol = baca_keyboard()         // fungsi dari library
    update(tombol)                   // kodemu
    gambar_sprite(pemain, posisi)    // fungsi dari library
```

**Framework** membalik arah itu. Framework yang memegang loop, lalu memanggil fungsi yang kamu isi pada saat yang tepat.

```text title="Pseudocode: memakai framework"
// kamu hanya mengisi fungsi-fungsi ini; framework yang memanggilnya
mulai():          siapkan pemain
update(delta):    gerakkan pemain
gambar():         gambar pemain
```

**Engine** juga memegang loop seperti framework, ditambah alat produksi: editor untuk menyusun dunia game, pengimpor yang mengubah file dari aplikasi lain menjadi data siap pakai, dan pembuat build untuk berbagai platform. Fungsi `Update()`, `Tick()`, dan `_process()` di [Pelajaran 1 Fondasi Engine](/belajar/fondasi-engine/01-frame/) adalah fungsi yang kamu isi dan engine yang memanggil.

| | Library | Framework | Engine |
| --- | --- | --- | --- |
| Yang memegang game loop | Kodemu | Framework | Engine |
| Editor visual | Tidak disediakan | Umumnya tidak disediakan | Umumnya disediakan |
| Pengimpor aset dan pembuat build | Kamu siapkan sendiri | Tergantung framework-nya | Disediakan |
| Contoh yang menyebut dirinya begitu | SDL, raylib, Three.js | MonoGame, LÖVE | Unity, Unreal Engine, Godot |

Situs SDL menyebutnya library lintas platform untuk mengakses audio, keyboard, mouse, joystick, dan hardware grafis. Situs raylib menulis terang-terangan bahwa raylib tidak menyediakan antarmuka visual, alat GUI, atau editor. Di Bab Tambahan [Web & Three.js](/belajar/web-threejs/01-frame/), [Three.js](/kamus/web/threejs/) dipakai dengan cara yang sama: game loop-nya ditulis sendiri dengan `requestAnimationFrame`.

Batas ketiganya tidak selalu tegas. Halaman depan LÖVE berjudul "Free 2D Game Engine", tetapi isinya menyebut LÖVE sebagai framework untuk membuat game 2D dengan Lua. Sebutan di halaman depan tidak banyak membantu. Untuk alat yang sedang kamu nilai, periksa saja baris-baris di tabel tadi.

Di dalam engine, komponen-komponen ini biasanya berupa subsistem terpisah yang saling memanggil. Dokumentasi Godot memperlihatkannya dengan jelas: rendering, physics, dan audio ditangani oleh *server* tingkat rendah (`RenderingServer`, `PhysicsServer2D`, `PhysicsServer3D`, `AudioServer`), dan sistem scene yang dipakai sehari-hari dibangun di atasnya. Engine lain menyusunnya dengan nama dan batas yang berbeda, tetapi pembagian kerjanya mirip.

Di luar daftar ini, isi engine makin beragam: UI, navigasi untuk AI, networking, terrain, dan banyak lagi. Sebagian engine menyediakannya sendiri, sebagian mengandalkan plugin atau paket tambahan, dan isinya bisa berubah dari versi ke versi. Saat membandingkan engine untuk sebuah proyek, cek kebutuhan proyekmu satu per satu terhadap daftar ini.

## Cara engine menyusun isi dunia

Setiap engine harus menjawab pertanyaan yang sama: apa satuan terkecil sebuah benda di dunia game, di mana datanya disimpan, dan di mana logikanya ditulis. Ada empat jawaban yang paling sering ditemui.

Supaya mudah dibandingkan, keempatnya dipakai untuk membuat benda yang sama: sebuah **peti** yang terlihat, bisa ditabrak, dan bisa dibuka pemain.

### Pohon node

Di model ini, setiap **node** punya satu jenis dan satu tugas. Node disusun menjadi pohon, dan pohon node yang disimpan sebagai file disebut **scene**. Sebuah scene bisa dipasang di dalam scene lain sebanyak yang kamu mau. Godot memakai model ini.

```text title="Pohon node (Godot)"
Peti (StaticBody3D)               ← skrip peti.gd menempel di sini
├── Model (MeshInstance3D)        ← menggambar mesh
├── Bentuk (CollisionShape3D)     ← bentuk untuk tabrakan
└── Suara (AudioStreamPlayer3D)   ← sumber suara
```

Kemampuan sebuah node datang dari jenisnya, dan jenis itu diturunkan dari jenis lain. Contoh dari dokumentasi Godot: `Sprite2D` adalah sebuah `Node2D`, sebuah `CanvasItem`, sekaligus sebuah `Node`, sehingga punya semua kemampuan ketiganya. Dokumentasi yang sama menyebut bahwa node Godot tidak bekerja seperti komponen di engine lain. Sebagian besar node berdiri sendiri, dan skrip menempel pada satu node untuk memperluas perilakunya.

Scene yang sudah disimpan bekerja seperti jenis node baru. Jika scene Peti dipasang di dua puluh tempat lalu scene aslinya diubah, kedua puluh peti itu ikut berubah.

### GameObject dan komponen

Di model ini, benda di dunia game adalah **GameObject**: wadah yang belum bisa apa-apa. Kemampuannya datang dari **komponen** yang dipasang padanya. Unity memakai model ini.

```text title="GameObject dan komponen (Unity)"
Peti (GameObject)
  Transform              ← selalu ada dan tidak bisa dilepas
  MeshFilter             ← data mesh yang dipakai
  MeshRenderer           ← menggambar mesh
  BoxCollider            ← bentuk untuk tabrakan
  AudioSource            ← sumber suara
  Peti (MonoBehaviour)   ← skripmu juga sebuah komponen
```

Dokumentasi Unity menyebut GameObject sebagai wadah untuk komponen, dan komponenlah yang menjalankan fungsinya. Setiap GameObject punya tepat satu komponen [Transform](/kamus/ruang/transform/). Skrip C# yang diturunkan dari `MonoBehaviour` selalu hidup sebagai komponen pada sebuah GameObject. GameObject juga bisa punya anak, jadi model ini tetap memakai [hierarki](/kamus/ruang/hierarchy/). Bedanya dengan pohon node: kemampuan peti dikumpulkan pada satu objek, tanpa harus dipecah menjadi anak-anak.

### Actor dan komponen

{/* Belum diverifikasi ke dokumentasi Epic (dev.epicgames.com diblokir proxy saat ditulis, 2026-10-30): Actor sebagai objek yang ditaruh di level; komponen bisa bertingkat di dalam satu Actor; transform Actor diambil dari root component; logika di C++ atau Blueprint. */}

Unreal memakai model yang mirip. Benda yang ditaruh di sebuah level disebut **Actor**, dan kemampuannya datang dari **komponen** yang dipasang padanya. Komponen di dalam satu Actor bisa disusun bertingkat, dan posisi Actor di dunia diambil dari komponen akarnya (*root component*).

```text title="Actor dan komponen (Unreal)"
BP_Peti (Actor)                  ← logika di Blueprint atau C++
  StaticMeshComponent (akar)     ← mesh; posisi Actor diambil dari sini
    BoxComponent                 ← bentuk untuk tabrakan
    AudioComponent               ← sumber suara
```

Logika gameplay ditulis di C++ atau di Blueprint, sistem pemrograman visual milik Unreal.

### ECS: entitas, komponen, sistem

Model keempat memisahkan data dan logika sepenuhnya. **Entitas** hanyalah nomor pengenal. **Komponen** hanya berisi data, tanpa fungsi. **Sistem** berisi logika dan berjalan atas semua entitas yang punya kombinasi komponen tertentu. ECS adalah singkatan dari *Entity Component System*.

```text title="Pseudocode: ECS"
entitas 42:  Posisi, Mesh, Collider, Peti { terbuka: salah }
entitas 43:  Posisi, Mesh, Collider, Peti { terbuka: benar }

sistem_buka_peti(pemain):
    untuk setiap entitas yang punya (Peti, Posisi):
        jika pemain dekat dan tombol aksi ditekan:
            Peti.terbuka = benar
```

Karena komponen sejenis bisa disimpan berdampingan di memori, sistem bisa membacanya dengan cepat dan pekerjaannya lebih mudah dibagi ke beberapa inti CPU. Keuntungan ini paling terasa saat jumlah objeknya sangat banyak. Artikel pengembang utama Godot tahun 2021 memberi contoh game yang membutuhkannya, seperti city builder, sandbox, dan sebagian game strategi dengan puluhan ribu unit, dan berpendapat bahwa kebanyakan game hanya punya ratusan objek.

Engine memakai ECS dengan cara berbeda. Bevy membangun seluruh logika engine dan game-nya di atas ECS, dengan komponen berupa struct Rust dan sistem berupa fungsi Rust. Unity menyediakan paket **Entities**, bagian dari DOTS, sebagai implementasi ECS di samping GameObject. Godot memakai pohon node untuk logika game, dan artikel tadi menjelaskan bahwa optimasi berorientasi data dipakai di dalam subsistem seperti rendering dan physics.

### Membandingkan keempatnya

| Model | Satuan dasar | Logika ditulis di | Cara menambah kemampuan |
| --- | --- | --- | --- |
| Pohon node | Node dengan satu tugas | Skrip pada node | Menambah node anak, atau memakai jenis node lain |
| GameObject dan komponen | GameObject sebagai wadah | Komponen skrip | Memasang komponen |
| Actor dan komponen | Actor | Kelas Actor atau komponen (Blueprint, C++) | Memasang komponen |
| ECS | Entitas berupa nomor | Sistem | Menambah komponen data pada entitas |

Ketiga model pertama sama-sama menggabungkan data dan logika dalam satu objek, dan enak dipakai untuk menyusun dunia secara visual di editor. ECS unggul saat objeknya sangat banyak, tetapi cara menulis kodenya cukup berbeda dari pemrograman berorientasi objek yang biasa diajarkan. Saat pindah engine, kenali dulu model yang dipakai engine tujuan supaya kebiasaan dari engine lama tidak ikut terbawa.

## Runtime dan editor: apa yang ikut ke build

Saat kamu menekan tombol Play di editor, game berjalan di dalam editor. Saat kamu membuat **build**, engine mengemas runtime dan data game-mu menjadi aplikasi terpisah untuk satu platform. Beberapa hal berubah di antara keduanya:

- **Alat editor tidak ikut.** Skrip yang menambah menu atau jendela di editor dipisahkan dan tidak masuk ke build.
- **Aset sudah diubah bentuknya.** Engine mengimpor file sumber (misalnya `.fbx` atau `.png`) menjadi data internal yang cocok untuk platform tujuan, dan data itulah yang dikemas. Kode yang membaca file sumber langsung dari folder proyek bisa berhasil di editor lalu gagal di build.
- **Satu build untuk satu platform.** Build Windows tidak bisa dijalankan di Android. Data seperti kompresi tekstur juga bisa berbeda per platform.
- **Cara kode dijalankan bisa berbeda.** Contohnya ada di tab Unity di bawah.
- **Performa berbeda.** Editor ikut memakai CPU dan memori, jadi angka untuk keputusan optimasi diambil dari build ([Fondasi 8](/belajar/fondasi-engine/08-profiling/)).

Di Play mode editor, kode C# selalu dijalankan oleh **Mono**, yang mengompilasi kode saat program berjalan (JIT). Build bisa memakai Mono atau **IL2CPP**. IL2CPP mengubah kode C# menjadi C++, lalu mengompilasinya ke kode mesin sebelum game dijalankan (AOT). IL2CPP wajib di beberapa platform yang tidak mendukung JIT, dan dokumentasinya punya halaman khusus tentang keterbatasannya.

Aset hasil impor disimpan di folder `Library` proyek, yang berfungsi sebagai cache. File sumbernya di folder `Assets` tidak diubah.

Build dibuat lewat **File → Build Profiles** (dulu bernama Build Settings). Setiap platform butuh build sendiri.

## Engine buatan sendiri

Engine buatan sendiri (*in-house engine* atau *custom engine*) adalah runtime dan alat produksi yang dibangun sendiri oleh sebuah studio, biasanya di atas beberapa library. Misalnya, sebuah tim memakai SDL untuk jendela dan input, memakai library physics yang sudah ada, lalu menulis sendiri renderer, format level, dan editornya. Skalanya beragam, dari kerangka kecil untuk satu game 2D sampai engine besar yang dipakai bertahun-tahun untuk banyak judul.

Perbandingannya dengan engine yang tersedia untuk umum, memakai kriteria yang sama:

| Kriteria | Engine yang tersedia untuk umum | Engine buatan sendiri |
| --- | --- | --- |
| Kendali atas cara kerja | Sebatas yang disediakan engine, kecuali kode sumbernya boleh dan bisa diubah | Penuh |
| Fitur yang tidak dipakai | Tetap ada di engine | Hanya yang dibutuhkan game |
| Editor, pengimpor, dan pembuat build | Sudah tersedia | Harus dibuat dan dirawat sendiri |
| Dukungan platform baru | Umumnya dikerjakan pembuat engine | Ditulis sendiri untuk setiap platform |
| Anggota tim baru | Bisa belajar dari dokumentasi, tutorial, dan komunitas | Harus dilatih dari dalam; dokumentasi ditulis sendiri |
| Ketergantungan | Pada keputusan pembuat engine | Pada anggota tim yang memahami engine-nya |

Pilihan ini paling masuk akal saat kebutuhan teknis game-nya memang tidak terpenuhi engine yang ada, dan timnya siap membiayai pembuatan alat-alatnya dalam jangka panjang. Pertimbangan biaya dan lisensi engine komersial dibahas di pelajaran tersendiri tentang lisensi dan model biaya.

Di luar keputusan produksi, menulis engine kecil sebagai latihan adalah cara yang baik untuk memahami tabel komponen tadi. Game loop dengan SDL atau raylib, ditambah satu sprite yang digerakkan dengan [delta time](/kamus/dasar/delta-time/), sudah menyentuh runtime, input, renderer, dan scripting.

## Membaca dokumentasi engine

Dokumentasi engine yang belum pernah kamu pakai lebih mudah dibaca kalau kamu tahu apa yang dicari. Urutan berikut bisa dipakai untuk engine apa pun:

1. **Cocokkan versinya.** Nama fungsi dan menu bisa berubah antarversi. Alamat dokumentasi Unity memuat nomor versi (misalnya `6000.0`), dan dokumentasi Godot punya pilihan versi seperti `stable`. Pastikan versinya sama dengan engine yang kamu pakai.
2. **Bedakan manual dan referensi API.** Manual menjelaskan konsep dan alur kerja. Referensi API mendaftar setiap kelas beserta properti dan fungsinya. Unity menamainya *User Manual* dan *Script Reference*. Godot membaginya menjadi *Manual* dan *Class reference*, dan referensi kelasnya juga bisa dibuka langsung dari editor skrip.
3. **Cari dengan nama lokal.** Setiap komponen di tabel tadi punya nama sendiri di setiap engine. Tabel di bawah bisa jadi titik awal.
4. **Baca rantai pewarisan.** Halaman sebuah kelas di referensi API mencantumkan kelas induknya. Di Godot, halaman `Node` menulis *Inherits: Object*. Di Unity, halaman `MonoBehaviour` menulis *Inherits from: Behaviour*. Properti yang tidak kamu temukan di halaman sebuah kelas sering ada di halaman induknya.
5. **Baca bagian keterbatasan dan catatan platform.** Halaman seperti *IL2CPP limitations* di Unity atau catatan ekspor per platform di Godot menjelaskan hal yang berbeda antara editor dan build.

| Benda di dunia game | GameObject | Actor | Node (atau scene yang dipasang) |

## Kesalahan umum

Dua kesalahan pertama baru terlihat setelah build dibuat. Dua berikutnya berkaitan dengan keputusan arsitektur: pindah engine dan membangun engine sendiri.

### Membaca file sumber aset langsung

```text title="✗ Keliru"
gambar = baca_file("aset/peta.png")   // file sumber, hanya ada di folder proyek
```

```text title="✓ Benar"
gambar = muat_aset("aset/peta.png")   // lewat sistem aset engine, ikut dikemas ke build
```

Di editor, file sumber ada di folder proyek. Di build, engine mengemas data hasil impornya, dan file sumbernya biasanya tidak ikut.

### Kode khusus editor tercampur dengan kode game

```text title="✗ Keliru"
// skrip gameplay
saat_kena_damage():
    editor.sorot_objek(diri)    // API editor untuk debug, tidak ada di build
```

```text title="✓ Benar"
saat_kena_damage():
    #jika EDITOR                // hanya dikompilasi saat berjalan di editor
        editor.sorot_objek(diri)
    #akhir
```

API editor tidak tersedia di build, sehingga build bisa gagal dikompilasi atau skripnya error saat dijalankan. Simpan kode seperti ini di tempat khusus editor, misalnya folder `Editor` atau blok `#if UNITY_EDITOR` di Unity.

### Memaksakan model scene dari engine lama

```text title="✗ Keliru"
// pola GameObject ditiru di Godot
Peti (Node3D)                  ← node kosong sebagai "wadah"
├── KomponenModel (Node)       ← skrip yang mencari mesh di tempat lain
└── KomponenFisika (Node)      ← skrip yang mengatur tabrakan sendiri
```

```text title="✓ Benar"
Peti (StaticBody3D)            ← jenis node yang sudah bisa ditabrak
├── Model (MeshInstance3D)
└── Bentuk (CollisionShape3D)
```

Di pohon node, kemampuan datang dari jenis node itu sendiri. Meniru pola komponen hanya menambah lapisan dan kode penghubung. Hal yang sama berlaku ke arah sebaliknya: di Unity, mesh, collider, dan skrip bisa dipasang sebagai komponen pada satu GameObject tanpa harus dibuatkan anak masing-masing.

### Membangun engine sebelum game-nya jelas

```text title="✗ Keliru"
bulan 1 sampai 6:  renderer, editor level, sistem aset
bulan 7:           mulai membuat prototipe game
```

```text title="✓ Benar"
minggu 1 sampai 4: prototipe dengan alat yang sudah ada
lalu:              catat kebutuhan teknis yang tidak terpenuhi, baru putuskan
```

Prototipe memperlihatkan kebutuhan teknis yang sebenarnya, sehingga keputusan membangun engine sendiri punya dasar yang bisa diperiksa.
